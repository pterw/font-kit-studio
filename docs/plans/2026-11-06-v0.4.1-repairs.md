# Font Kit Studio 0.4.1 Implementation Plan

Status: planned (2026-11-06).
Implementation branch: `fix/v0.4.1-repairs` (cut from the head of the branch that carries the audit record and this plan; a docs sibling
branch alone edits the roadmap).
Base: the head of the branch that carries the audit record and this plan. Every `file:line` below is read at `5bd655e` (0.4.0 plus its
publication record). The Asteria change and the roadmap and spec edits move lines, so each brief re-reads its cause at its own BASE before slicing.

A task states behaviour, frozen interfaces and acceptance checks; the brief written from it adds the code-level detail.

**Goal:** repair what 0.4.0 does wrong on real apps, as found by the [real-app audit](../implementation/audit-2026-11-06-real-apps.md): lost
or misleading results first, then small fixes, then the README and the 0.4.1 release point.

**Architecture:** no new capability, no new message type and no new format. Fixes land as atomic commits on one branch, cheap and contained
ones first. The one fix that touches what the wire page version does (D2-10) lands last and can be cut to 0.4.2 without touching an earlier
commit. Warnings that stand in for a later repair (B08, D2-11, B19) share one warning channel that already exists.

**Tech stack:** vanilla JavaScript in two files (`fontkit-studio.html`, `fontkit-bridge.js`), stdlib Python (`scripts/serve.py`), Node
built-ins (`packages/fontkitstudio`), Python unittest with Playwright.

Rulings of 2026-11-06 behind this scope: 0.4.1 is the repair release, before any pip work; 0.4.1 holds the repairs (the 24 audit rows, of
which C2-8b is one) and 0.4.2 holds the pip wrapper, C2-3a and C2-2d; the work ships as four pull requests, the implementation branch last, with the page-version
change last and then the README and the release point; commits are atomic and scoped to one change, for rollback; the roadmap stays bounded.

## Global constraints

- Scope is the 24 audit rows homed to 0.4.1, Tasks 15 and 16 (the bridge-side and Studio-default residue of the repository Studio was written
  in), and the README and release point. Tasks 15 and 16 stay in 0.4.1 to finish stripping Asteria, although the audit record homes G1-3 and
  G2-18 to `later`. Nothing in "Non-goals" is touched.
- Version labels stay 0.4.0 until the release-point commit (Task 19). The export format version (`0.1.1`) and the bridge protocol version (1)
  do not change; a task that needs either to change names why and waits for a ruling.
- Studio remains one HTML file and the bridge one dependency-free script. Python is stdlib only; the npm package has zero runtime dependencies
  (global rule 8). Rule of three before an abstraction. Studio shows what the target acknowledged (global rule 1), never what it hoped for.
- Binding D-numbers: D016 (auto selectors are unstable), D039 and D044 (version labels), D050 and D065 (PR size; Markdown not counted),
  D063 and D066 (what advances the wire `pageVersion`), D072 (a `var()` family is refused). A task that would contradict one stops and asks
  for a ruling.
- Every new user-facing string is listed in "New strings" and approved before its task is dispatched.
- Tests assert what a user or the page observes, with an independent oracle (a literal, a second run, the page's computed style, a plan or
  deviation text), never the implementation. Each new test carries a Given/When/Then docstring, and a realistic break of the fix is shown
  failing. Real-app reruns use the two audited apps only as read-only targets. A dev server runs inside the job-object guard and is
  stopped by PID; the Next app runs as `next build` then `next start`. Never request a 404 route on the Next app.
- One atomic commit per audit row. A task that fixes several rows lands them as separate commits, in the order listed. Commits carry
  no process state (AGENTS.md anti-pattern 15) and no attribution trailer.
- The branch stays within D050 (8,000 material lines; Markdown reported separately, D065). This plan expects well under 2,000.
- Studio landings always run `test_studio_roles`, `test_role_routes` and `test_r2_integration`, plus the task's own tests.
- Procedure and role contracts: `AGENTS.md`. Durable events go to `docs/implementation/progress.md`; rulings go to `deviations.md`. The
  controller owns both and the CHANGELOG ledger lines named in Task 18.
- D-numbers: D078 is taken by the Asteria decision. This plan expects D079 (the warning kinds, Task 10) and D080 (Clear and a stale
  version, Task 17); confirm each is free in `deviations.md` at dispatch.

## Binding message contract (before any parallel Studio and bridge work)

Studio and the bridge exchange the protocol-1 messages already in the tree. This release adds no message type and no field outside `kind`.

| Message | Direction | Binding for 0.4.1 |
|---|---|---|
| `design:warning` | bridge to Studio | Already carries `requestId`, `targetId`, `kind` and `message` (bridge `noteRuntimeError`, near line 2251). Studio's `noteWarning` (near line 6396) accepts only `kind: "runtime-error"`. Tasks 10, 11 and 12 add three further `kind` values, `token-not-applied`, `edit-not-reapplied` and `edit-reapply-stopped`, with the same `message` (at most 300 characters) and `targetId` rules. Additive; the protocol version stays 1; recorded as D079 (Decision 1). |
| `design:applied`, `design:detected`, `design:roles-applied` and every other message | both | Unchanged. |
| Wire `pageVersion` | bridge to Studio | Advances only as D063 and D066 say. Task 17 alone changes how Clear treats a stale version, and only after its addendum and D080. |

Phasing: Studio learns the new `kind` values first (Task 10, Studio side), so an older or newer peer ignores an unknown kind; the bridge tasks
that send them (11, 12) land after it. Where Studio and the bridge must refuse the same value, the second task is phased on the first's patch
(none arises in 0.4.1: the content-model guard in Task 5 is bridge-only, because Studio has no copy of it).

### Task 1: Detect on a page with a closed `<details>` completes the first time (C1-1)

**Wave:** 1. **Touches:** `fontkit-bridge.js` (2175-2185, and `renderedRoleText` at 1427 if the fix needs it); `tests/test_role_detection.py` or
`tests/test_bridge_runtime.py`. **After:** none; it lands first. **Mode:** code.

**Cause.** The scan decides which text elements exist at its start and checks the same set at its end (`rendered.size !== styles.size`, then
`page-changed`). Text inside a closed `<details>` is not drawn at the start and is drawn at the end, so the first press fails with nothing
changed. That alone does not say why the second press completes, so the implementer shows the first-versus-second difference (what the set
holds at each press) before the fix, not only the test. S06 is not the cause (no mutation was recorded). This is not a page-version change:
nothing in D063 or D066 moves.

**Required behaviour.** The first Detect on a page with a closed `<details>` ends complete, with the same roles and parent count the second
press finds. A real page change during the scan still ends it as `page-changed`.

- [x] A fixture page with text in a closed `<details>`: the first press completes (given a fresh connection, when Detect runs once, then the
  result is complete and equals the second press's role list).
- [x] The bundled demo page shows the same fix (the audit saw it there too).
- [x] A real change during the scan (a visible text node inserted mid-scan) still ends `page-changed`; show the test failing if the fix
  ignores all mismatches.
- [x] Commit: `fix(bridge): count closed details text the same at both ends of a Detect scan`.

## Addendum 2 (2026-11-06): load, Task 1, and Task 9

1. **Load.** At most five browser runs at once, reviewers counted, with a health read before each dispatch. The limit drops back to four if free commit
   falls below 25 GB, load stays above 85%, or a test times out under load. This replaces "at most four phases" in Load.
2. **What Task 1 counts.** Text in the body of a closed `<details>` counts as rendered at both ends of a Detect scan, by a rule in `renderedRoleText` that
   reads no rects. Hidden text inside the body stays excluded, and `<summary>` and open-details text keep the rect test. The cause is lazy layout: a closed
   body has no rects until it is read, and reading them lays it out.
3. **How Task 1 is proved.** The bundled demo page is the stable failing case at the base. A small fixture page is not: it passes there about half the time,
   because layout state decides. So the demo test covers the plan's first check, and no fixture test is kept. A real change during the scan is shown with an
   animation, because a DOM insert is caught by page-version freshness before the end check.
4. **Task 9** runs as two phases, S08 and then C2-5c on its patch. The `beforeunload` tests wait for the page's close event or use a cancelable probe, because
   a close returns before its dialog arrives.
